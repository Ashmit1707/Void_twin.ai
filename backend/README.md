# DigitalTwin.ai — Backend

FastAPI service. Adds real ML (Isolation Forest anomaly detection) on top
of the same rule-based risk formula the frontend already computes
client-side, so both paths agree.

## Setup

```bash
cd backend
pip install -r requirements.txt
uvicorn main:app --reload --port 8000
```

Visit `http://localhost:8000/docs` for interactive API docs (auto-generated by FastAPI).

## Endpoints

| Method | Path | What it does |
|---|---|---|
| GET | `/api/health` | Liveness check |
| GET | `/api/demo` | Returns the same 12-station demo scenario the frontend has hardcoded (Paint-12 drift) |
| POST | `/api/upload` | Upload a CSV, get back scored stations |

## CSV Format (same as the frontend expects)

```
station_id,station_name,zone,time_step,cycle_time_sec,queue_depth,utilization_pct,takt_target_sec,sensor_coverage
P-12,Paint-12,Paint,0,54,2.1,70,52,yes
P-12,Paint-12,Paint,1,58,3.0,75,52,yes
```

Required: `station_id`, `zone`, `cycle_time_sec`, `queue_depth`, `utilization_pct`
Optional: `station_name`, `time_step`, `takt_target_sec` (default 60), `sensor_coverage` (default yes)

## How Scoring Works

1. **Rule-based risk** (`predictor.py: compute_rule_based_risk`) — identical formula to
   `design/components/csv.js: computeRiskForRow`. Three signals: cycle time deviation
   from takt, queue depth, utilisation. This is the explainable SPC-style layer.

2. **Isolation Forest anomaly score** (`predictor.py: compute_anomaly_scores`) — fits a
   model per station on its own (cycle_time, queue_depth, utilization) history. Needs
   at least 4 rows for that station; below that, falls back to anomaly = 0 (not enough
   history yet — same "partial data still works" story as the sensor-poor stations).

3. **Final risk** = 85% rule-based + 15% anomaly score, blended per row.

## Response Shape

Matches the `STATIONS` array shape the frontend already uses in `data.js` — same
`id, name, zone, queue, takt, util, sensor, risk[], factors{}, confidence` fields.
This means the frontend can eventually fetch from `/api/upload` or `/api/demo`
instead of parsing CSVs client-side, with zero changes to `timeline.js`, `table.js`,
or `insight.js` — they just read from `STATIONS`, wherever it came from.

## Not Yet Wired Up

The frontend (`index.html`) currently parses CSVs entirely client-side and never
calls this API. Hooking them together is a small change — swap the `processCSVFile()`
call in `index.html` for a `fetch('http://localhost:8000/api/upload', ...)` — but
means the dashboard demo now depends on this server running. Worth doing once the
CORS/local-server setup is confirmed to work reliably for a live pitch.

## Known Limitations (say this in the pitch, don't hide it)

- Isolation Forest per station is refit on every request — fine for a demo, not for
  production (would want persisted models updated incrementally)
- No database — everything is stateless, in-memory per request
- No auth — wide-open CORS, fine for local demo only
